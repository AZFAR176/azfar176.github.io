Critic feedback for Text-to-SQL retries

From EnterpriseSQL-RL: how the runtime decides to accept, retry, or abstain, and what diagnostic is passed back to the policy.

The trained generator is not used as an isolated SQL writer. At inference it sits inside an agent that retrieves schema context, generates a candidate, validates it, executes it in a sandbox, and only then applies a query-conditioned semantic critic. If any stage fails, the agent retries with a diagnostic from the stage that failed. This critic is an inference-time controller. It is not a GRPO reward.

Why the critic exists

A query can be syntactically valid, schema-valid, and executable, and still fail to represent the user request. Typical cases include using COUNT instead of SUM, dropping a location or temporal filter, inverting a ranking, or grouping at the wrong granularity. Deterministic checks cannot catch these intent errors, so the critic is invoked only after static validation and successful execution.

What the critic sees

The critic compares the user request q, a short dialogue context hq used only to resolve references, the constructed SQL y, and an execution-result summary τexec = (result columns, row count, bounded sample rows).

It does not receive the database schema, retrieval results, or join metadata. It is not allowed to re-check table or column existence, aliases, or join legality, and it must not invent schema elements that are not already in y. Those checks belong to the deterministic validator. The split is intentional: the validator asks whether the SQL is legal to run; the critic asks whether the executed SQL preserved the request.

How the critic decides

It extracts explicit request conditions (entities, measures, filters, temporal constraints, grouping, ranking, limits, and expected output) and compares them with an interpretation of the constructed SQL and the observed result. Each condition is marked satisfied, violated, missing, or uncertain. An equivalent SQL formulation is not treated as an error. Result samples are used only as evidence of an observable contradiction; an empty result is not automatically a failure, and an unusual value alone is not enough to reject a query.

The critic returns one of three decisions:

  • Pass — no concrete request–SQL contradiction was found. This is not a proof of correctness.
  • Retry — at least one explicit condition is missing or violated. The critic must name the unmet condition, the conflicting or missing SQL operation, the supporting evidence, and one intent-level repair instruction. It must not propose new schema.
  • Abstain — the request is materially ambiguous and needs clarification. Confidence alone is not a retry signal.

What feedback is sent on a retry

Validation is ordered. A retry is triggered if static validation fails, if sandboxed execution fails or times out, or if the critic returns Retry. The diagnostic passed to correction depends on which stage failed:

  • Static diagnostic — parser errors, unknown identifiers, invalid aliases, illegal joins, prohibited operations, or format violations.
  • Execution diagnostic — database exceptions, timeouts, or other sandbox failures.
  • Semantic diagnostic — only the unmet request condition, supporting SQL or result evidence, and an intent-level repair instruction. The critic says what part of the request was not preserved; it does not rewrite the SQL.

On retry, the policy receives the original request, the retrieved schema (even though the critic never saw it), the previous SQL, and this diagnostic. The correction step is required to fix the diagnosed issue while preserving already-satisfied conditions, and it may use only tables, columns, and joins present in the supplied schema. Every corrected candidate re-enters the pipeline from the beginning. The loop is bounded by a retry budget K. If nothing passes, the runtime clarifies or abstains.

Relation to training

GRPO training uses a gated execution / AST / n-gram reward. The semantic critic is not part of that objective. Training teaches the generator to produce executable, structurally closer programs; the critic is reserved for accept / retry / abstain decisions at inference.
